# RAG 知识库模块实现方案

## 一、整体架构

```
用户/设备触发
    │
    ▼
┌─────────────┐   命中   ┌──────────────┐
│  规则引擎    │ ───────→ │  直接输出建议  │  (零幻觉, 零延迟)
│  R001-R005  │          │  advice_template
└──────┬──────┘          └──────────────┘
       │ 未命中/置信度不足
       ▼
┌─────────────┐   高置信  ┌──────────────┐
│  RAG 向量检索│ ───────→ │  LLM 生成建议  │  (结构化 JSON 输出)
│  pgvector    │          │  解析入库     │
└──────┬──────┘          └──────────────┘
       │ 相似度 < 阈值
       ▼
┌──────────────────────┐
│  降级: 使用原始数据    │  (不调 LLM, 避免幻觉)
│  + 硬逻辑兜底建议     │
└──────────────────────┘
```

**核心原则**: 只要有可能是幻觉产生的结果，都进行降级处理。

## 二、向量数据库：pgvector（已确定）

- **存储**: `knowledge_chunk.embedding vector(512)` — schema.sql 已定义
- **索引**: HNSW, `vector_cosine_ops`, m=16, ef_construction=64
- **规模**: 初始 30-100 篇文献 → 3000-10000 chunks → pgvector 轻松应对
- **并发**: 农业监测系统 QPS < 10，单 pgvector 实例足够
- **不需要** Milvus/Pinecone 等独立向量数据库

## 三、Python RAG 微服务（`navel-orange-rag/`）

### 3.1 技术栈

| 组件 | 选型 | 说明 |
|------|------|------|
| 框架 | FastAPI | 轻量, 异步, 自动生成 OpenAPI 文档 |
| Embedding | bge-small-zh (HuggingFace) | 512维, 中文优化, 本地推理 |
| LLM | OpenAI 兼容 API | GPT-3.5 / Qwen-7B, 可配置切换 |
| 数据库连接 | psycopg2 / asyncpg | 连接已有 PostgreSQL + pgvector |

### 3.2 服务端点

```
POST /embed          — 文本向量化 (文档处理时调用)
POST /search         — 向量检索 (返回 TopK chunks + 相似度)
POST /qa             — RAG 问答 (检索 + LLM 生成)
POST /process-doc    — 文档处理 (分块 + 向量化 + 入库)
GET  /health         — 健康检查
```

### 3.3 配置项


## 四、检索策略（已有 + 补充）

### 4.1 三种检索策略（已设计）

| 策略 | 触发场景 | Query 构建 |
|------|----------|-----------|
| 防治检索 | 设备识别到病害 | `"{病害名} 防治方案 药剂 温度{temp} 湿度{hum}"` |
| 诊断检索 | 农户描述症状 | `"{症状描述} 症状 特征 诊断"` |
| 物候检索 | 农事日历定时 | `"{物候期} {节气} 防治重点"` |

### 4.2 新增：多因素融合检索

当有环境数据 + 病害检测结果时，构建更精确的查询：

```python
def build_query(disease_code, temperature, humidity, phenology):
    parts = [DISEASE_NAMES[disease_code]]
    
    # 温度条件
    if temperature > 30: parts.append("高温")
    elif temperature < 10: parts.append("低温")
    
    # 湿度条件
    if humidity > 85: parts.append("高湿")
    
    # 物候期
    parts.append(f"{phenology}期防治")
    
    return " ".join(parts)
```

### 4.3 置信度判定与降级

```
if max_similarity >= 0.80:    → 高置信, 直接用 LLM 生成
elif max_similarity >= 0.70:  → 中置信, LLM 生成 + 标注"仅供参考"
elif max_similarity >= 0.50:  → 低置信, 降级到模板建议, 不调 LLM
else:                         → 无匹配, 使用硬逻辑兜底
```

### 5.1 Prompt 模板

```
  "advice": "防治建议（200字以内）",
  "medicine": ["推荐药剂1", "推荐药剂2"],

  "source_confidence": "high/medium/low",
  "reasoning": "判断依据（100字以内）"

```

### 5.2 不同场景的输出处理

| 场景 | 输出去向 | 格式要求 |
|------|----------|----------|
| 预警建议 | `alert_message.advice` 字段 | 结构化 JSON → 拆分 advice + medicine |
| 知识问答 | 直接返回前端 | 自然语言 answer + 来源 chunks |
| 农事日历提醒 | `farming_calendar.ai_advice` 字段 | 纯文本建议 |
| 诊断分析 | 日志 + 可选入库 | JSON 全量存储 |

### 5.3 Java 端解析

```java

public class RagAdvice {
    private String diseaseName;
    private String riskLevel;      // L1/L2/L3
    private String advice;         // 防治建议
    private List<String> medicine;
    private List<String> precautions;
    private String sourceConfidence; // high/medium/low
    private String reasoning;
}

// 使用 Jackson 解析
RagAdvice advice = objectMapper.readValue(llmResponse, RagAdvice.class);
```

### 5.4 LLM 输出校验 + 降级

```java
public RagAdvice safeParseAdvice(String llmResponse, AlertRule rule, EnvironmentData env) {
    try {
        RagAdvice advice = objectMapper.readValue(llmResponse, RagAdvice.class);
        // 校验必填字段
        if (advice.getAdvice() == null || advice.getAdvice().isBlank()) {
            return fallbackAdvice(rule, env);  // 降级
        }
        // 校验 risk_level 合法性
        if (!VALID_LEVELS.contains(advice.getRiskLevel())) {
            advice.setRiskLevel(String.valueOf(rule.getLevel()));  // 用规则引擎的等级
        }
        return advice;
    } catch (JsonProcessingException e) {
        return fallbackAdvice(rule, env);  // JSON 解析失败, 降级
    }
}
```

## 六、知识库管理

### 6.1 三层去重（已设计）

| 层级 | 方法 | 阈值 |
|------|------|------|
| 文件级 | SHA256 hash 比对 | 完全相同 → 跳过 |
| 分块级 | SHA256 hash 比对 | 完全相同 → 合并 |
| 语义级 | 余弦相似度 | > 0.95 → 去重 |

### 6.2 防止无关数据污染

```java
// 上传时领域关键词验证
private static final List<String> DOMAIN_KEYWORDS = List.of(
    "脐橙", "柑橘", "溃疡病", "黄龙病", "炭疽病", "缺素",
    "防治", "药剂", "施肥", "修剪", "物候", "花期", "果实",
    "虫害", "红蜘蛛", "木虱", "蚜虫", "土壤", "灌溉"
);

boolean isRelevant(String text) {
    long count = DOMAIN_KEYWORDS.stream()
        .filter(kw -> text.contains(kw))
        .count();
    return count >= 3;  // 至少命中 3 个领域关键词
}
```

### 6.3 审核流程

```
上传文献 → status=0(待处理)
    → 文本提取 → 领域验证
       不通过 → status=3(处理失败), error_message
    → 分块 + 向量化 → status=2(已完成)
    → review_status=0(待审核)
    → 管理员审核: 通过(1) / 驳回(2)
    → 通过后才参与检索
```

### 6.4 用户反馈进入知识库

```
农户提交反馈 (user_feedback)
    → 管理员确认有效 (dataset_tag = "已验证")
    → 导出为知识文档 (source = "USER_FEEDBACK")
    → 进入标准处理流程 (分块 → 向量化 → 审核)
    → 审核通过后参与 RAG 检索
```

## 七、补充考虑

| 项目 | 方案 |
|------|------|
| **Embedding 缓存** | 查询结果缓存到 Redis, TTL 1h, 避免重复向量化 |
| **LLM 调用限流** | 令牌桶限流, 防止突发请求打爆 API 配额 |
| **LLM 超时降级** | 15s 超时 → 返回模板建议, 不阻塞主流程 |
| **成本控制** | 优先用 Qwen-7B (便宜), GPT-3.5 作为备用 |
| **向量维度一致性** | bge-small-zh 固定 512 维, schema.sql 已约束 vector(512) |
| **文档更新** | 更新文献时: 删除旧 chunks → 重新分块向量化 |
| **检索结果排序** | 先按相似度排序, 同分时按 document.review_status 优先 |
| **多语言** | bge-small-zh 只支持中文, 英文文献需翻译后再入库 |
| **监控** | 记录每次检索: query / top_k 结果 / 相似度 / LLM 耗时 / 是否降级 |

## 九、验证方式

1. **单元测试**: embedding 输出维度 = 512, 余弦相似度计算正确
2. **集成测试**: 上传一篇病害文档 → 分块 → 向量化 → 检索 → 验证 TopK 结果
3. **端到端测试**: 模拟设备上报病害 → 规则未命中 → RAG 检索 → LLM 生成建议 → 解析入库
4. **降级测试**: 关闭 LLM 服务 → 验证降级到模板建议 → 验证数据未被污染
5. **去重测试**: 上传同一文档两次 → 验证第二次被跳过
